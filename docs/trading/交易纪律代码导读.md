## 定时任务实际调用顺序

1. [`scheduler.main()`](../../backend_api_python/app/commands/scheduler.py) 取得数据库租约后创建观察器。主循环约每 10 秒调用 `tick()`，`tick()` 到下一整点且上一轮已结束时才启动后台线程。启动 Scheduler 或登录网页都不会立即扫描仓位。
2. [`HourlyDisciplineObserver._run()`](../../backend_api_python/app/trade_discipline/observation.py) 根据 `TRADE_DISCIPLINE_USER_ID` 读取该用户所有已保存的交易所凭证。一个账户失败会记录 `account_failed` 并继续扫其他账户。
3. [`observe_account()`](../../backend_api_python/app/trade_discipline/observation.py) 复用持仓页的快照和管理登记，记录 `snapshot_read`。定时判定当前集中于币安永续。快照失败或不完整时输出待复核。已有管理登记的仓位通常标记 `already_managed`。已有实盘策略登记了部分数量，且实际仓位大于登记总量时，只走通知分支。
4. [`read_position_evidence()`](../../backend_api_python/app/trade_discipline/position_evidence.py) 优先回放本地成交，证据不足才按合约补查交易所。数量要与快照对得上。反手会拆成旧方向平仓量和新方向开仓量。成交时间用于定位当前仓位，订单提交时间用于查计划和行情。产品身份按目录或当前账户环境的交易所合约信息核对，USDT 和 USDC 保持各自原生合约。订单事件同时保留完整 `client_order_id`，本地缺字段才查询原单。
5. [`assess_manual_opening()`](../../backend_api_python/app/trade_discipline/manual.py) 依次判断开仓来源、计划和 EMA25。[只读归属查询](../../backend_api_python/app/trade_discipline/origin.py) 按原生合约、用户、凭证和完整订单号码查现有绑定、待执行、网格及快捷交易记录，也兼容币安发单时添加 broker 前缀的格式。开启 `TRADE_DISCIPLINE_EXTERNAL_OPENINGS_AS_MANUAL` 表示确认该用户账户没有第三方自动交易，查询完整且排除系统单后识别外部人工单。`ios_im_` 是来源线索。数据库失败、号码冲突、未确认系统提交或系统历史已清理时待复核。Demo 逐单调试标记继续兼容。加仓只核对归属，计划和 EMA25 只判断当前仓位的开仓订单。
6. [`apply_poll_window()`](../../backend_api_python/app/trade_discipline/manual.py) 把首次通过的自然小时和计划版本存入 PostgreSQL。同一小时内重复触发仍是同一轮。下一个观察轮次中，仓位仍符合未管理等条件才列为拟接管。重启后继续使用原通过记录。

## 开仓判断的分支

| 判断结果 | 当前行为 | 调试位置 |
| --- | --- | --- |
| 确认由策略或系统开仓 | `skipped / system_opening` | [`opening_order_origin()`](../../backend_api_python/app/trade_discipline/manual.py) |
| 手动仓位混入策略敞口，或实盘策略只登记了部分数量 | `notify_only`，走浏览器通知 | [`assess_manual_opening()` 和 `apply_poll_window()`](../../backend_api_python/app/trade_discipline/manual.py) |
| 开仓、数量或归属证据不足 | `needs_review` | [`_observe_position()`](../../backend_api_python/app/trade_discipline/observation.py) |
| 无匹配的有效计划 | `proposed_exit / no_plan`，本轮跳过 EMA25 | [`check_plans()`](../../backend_api_python/app/trade_discipline/observation.py) |
| 缺下单时间或计划查询失败 | `needs_review / plan_evidence_unavailable` | [`PlanService.match_at_order_time()`](../../backend_api_python/app/trade_plans/service.py) |
| 有计划，EMA25 方向不符 | `proposed_exit / ema25_direction_blocked` | [`check_ema25_at_order_time()`](../../backend_api_python/app/trade_discipline/ema.py) |
| 有计划，行情缺失或无法验证 | `needs_review / ema_evidence_unavailable` | [`check_ema25_at_order_time()`](../../backend_api_python/app/trade_discipline/ema.py) |
| 计划和 EMA25 都通过 | 首轮 `waiting_for_next_poll`，后续符合条件时 `proposed_adoption` | [`apply_poll_window()`](../../backend_api_python/app/trade_discipline/manual.py) |

计划使用实际下单时已有的版本，按品种、交易所、产品、实际结算币和方向匹配。只认当时已经进入观察中的计划，按进入观察时间计算默认 24 小时窗口，多份匹配选择最近进入观察中的有效计划，编辑版本不刷新窗口。EMA25 使用下单前最后一根已收盘的 K 线，加密货币用 4 小时，股票规则在快捷开仓入口使用 1 小时。高于 EMA25 只允许做多，低于只允许做空，相等时多空均满足该项。

## 拟退出与拟接管之后

- **退出**。开启自动退出后，Scheduler 用 [`queue_observed_exit()`](../../backend_api_python/app/trade_discipline/exit.py) 登记请求，将开仓及原有加仓的完整客户端订单号保存在现有请求 JSON。Trading Worker 复核实时仓位、成交与归属，数量上限取本轮可确认值，沿用保存的违规结论。后续计划或行情变化不重新改变原开仓结论。发出请求前保存退出订单自身的客户端订单号。超时或重启后，已提交记录按原订单号回查。
- **接管**。开启自动接管后，[`adopt_observed_position()`](../../backend_api_python/app/trade_discipline/adoption.py) 用原计划版本生成并校验参数，复核仓位、管理归属和未成交开仓单，再复用整仓接管流程。策略由原有策略命令启动，重复触发或异常恢复用接管键查找原实例。
- **启动失败**。即时启动失败及下一轮发现的异步命令失败，由 [`notify_management_start_failures()`](../../backend_api_python/app/trade_discipline/notifications.py) 复用站内通知，同一失败记录只通知一次。保留原实例供人工处理，人工停止命令不触发本项失败通知。
- **退出异常**。原单已确认零成交终止时，下一轮可以继续同一逻辑请求，历史尝试保存在原 JSON，每次使用不同客户端订单号。结果仍不明确时继续查原单并通知人工，不重复提交。
- **查看一轮结果**。按 `round_started`、`snapshot_read`、`fill_replay`、`origin_lookup`、`opening_origin`、`plan_check`、`ema25_check`、`position_decision`、`round_finished` 找终端日志。`origin_lookup` 记录匹配的表与记录编号，或具体待复核原因。走了提前返回分支时，后面的判定日志会缺席。

## 关键操作通知入口（2026-11-28 修订）

| 入口 | 所属进程 | 做什么 |
| --- | --- | --- |
| `HourlyDisciplineObserver._observe` → `notify_observation` | Scheduler | 登记首次通过、退出请求、接管请求及人工处理分支；空仓和常规已管理不刷消息 |
| `_save_order` → `notify_exit_request` | Trading Worker | 先读回原快捷交易行，再登记真实成交量和均价；不能拿拟退出数量声称成交 |
| `_sync_discipline_notices` → `process_discipline_notices` | Trading Worker | 恢复原退出结果漏通知、核对真实启动命令、将待发送记录补入原队列；不重新下单 |
| `record_notice` | 原调用进程内的短事务 | 按业务事件键去重并留下站内事实，读取个人设置的默认渠道；不发外部网络请求 |
| `trade_discipline_notice` → `deliver_notice` | 原 Celery Worker 的 maintenance 队列 | 复用发送器按渠道投递；成功、失败、用户取消渠道分别保存，失败最多尝试三次 |

新代码位于原 `app/trade_discipline/notifications.py`、薄投递模块 `notice_delivery.py` 和一个有限 Celery 任务。复用 `qd_strategy_notifications` 的 JSON 载荷，不新增通知表、字段、索引或常驻进程。

查看通知时区分三层证据：站内记录已创建、各外部渠道已接收、用户实际看见。日志中的 `notice_record_failed`、`notice_queue_unavailable`、`notice_delivery` 分别对应持久化、入队和渠道结果。投递日志不输出渠道 URL、token 或签名密钥。恢复补齐的真实旧成交会标为“恢复补记”，不能把它说成原来已经即时发送过。

自动接管模板的 ATR 规则尚待需求方确认，不能仅把一个开关改成 true 就宣称整套业务全部投产。系统快捷开仓拦截属于原快捷下单入口，本项客户端手动仓位监控不依赖该功能。
