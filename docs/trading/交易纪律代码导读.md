# 交易纪律代码导读

## 从这里进入

| 要调试的流程 | 进程与代码入口 | 第一个断点 |
| --- | --- | --- |
| 每小时检查交易所手动开仓 | Compose 的 `scheduler-worker` 执行 `python -m app.commands.scheduler`。[Scheduler 入口](../../backend_api_python/app/commands/scheduler.py) | `main()` 内的 `observer.tick(...)` |
| 网页或 Agent 快捷开仓下单前检查 | HTTP API 调用同一个 [快捷开仓守卫](../../backend_api_python/app/trade_discipline/entry_guard.py) | `entry_discipline_rejection()` |
| 执行或回查纪律退出请求 | Trading Worker 的 [退出轮询](../../backend_api_python/app/services/pending_order_loops.py) 读取 Scheduler 登记的请求 | `_sync_discipline_exits()`，再进 [`_process_exit()`](../../backend_api_python/app/trade_discipline/exit.py) |

VS Code 中选择「完整项目：调试 Scheduler」。已连接进程时，在 `HourlyDisciplineObserver.tick()` 的 `if` 行暂停，在调试控制台执行 `self._next_run = now`，然后继续运行。若上一轮线程仍活着或观察器已停止，这次调用会跳过。观察线程的实际起点是 `_run()`。运行任务「完整项目：查看后台日志」可在终端看完整一轮。

## 定时任务实际调用顺序

1. [`scheduler.main()`](../../backend_api_python/app/commands/scheduler.py) 取得数据库租约后创建观察器。主循环约每 10 秒调用 `tick()`，`tick()` 到下一整点且上一轮已结束时才启动后台线程。启动 Scheduler 或登录网页都不会立即扫描仓位。
2. [`HourlyDisciplineObserver._run()`](../../backend_api_python/app/trade_discipline/observation.py) 根据 `TRADE_DISCIPLINE_USER_ID` 读取该用户所有已保存的交易所凭证。一个账户失败会记录 `account_failed` 并继续扫其他账户。
3. [`observe_account()`](../../backend_api_python/app/trade_discipline/observation.py) 复用持仓页的快照和管理登记，记录 `snapshot_read`。定时判定当前集中于币安永续。快照失败或不完整时输出待复核。已有管理登记的仓位通常标记 `already_managed`。已有实盘策略登记了部分数量，且实际仓位大于登记总量时，只走通知分支。
4. [`read_position_evidence()`](../../backend_api_python/app/trade_discipline/position_evidence.py) 优先回放本地成交，证据不足才按合约补查交易所。数量要与快照对得上。反手会拆成旧方向平仓量和新方向开仓量。成交时间用于定位当前仓位，订单提交时间用于查计划和行情。当前回溯入口只接受 USDT 永续，因此 USDC 仓位可出现在快照中，回溯却会停在 `position_evidence_unavailable`。
5. [`assess_manual_opening()`](../../backend_api_python/app/trade_discipline/manual.py) 依次判断开仓来源、计划和 EMA25。优先查系统订单归属，无法证明外部订单为手动时记作未知。调试可用 `TRADE_DISCIPLINE_MANUAL_ORDERS_JSON` 精确标记已确认的外部订单。加仓只核对归属，用于识别混入的策略敞口。计划和 EMA25 的时间仍取当前仓位的开仓订单。
6. [`apply_poll_window()`](../../backend_api_python/app/trade_discipline/manual.py) 把首次通过的自然小时和计划版本存入 PostgreSQL。同一小时内重复触发仍是同一轮。下一个观察轮次中，仓位仍符合未管理等条件才列为拟接管。重启后继续使用原通过记录。

## 开仓判断的分支

| 判断结果 | 当前行为 | 调试位置 |
| --- | --- | --- |
| 确认由策略或系统开仓 | `skipped / system_opening` | [`opening_order_origin()`](../../backend_api_python/app/trade_discipline/manual.py) |
| 手动仓位混入策略敞口，或实盘策略只登记了部分数量 | `notify_only`，走浏览器通知 | [`assess_manual_opening()` 和 `apply_poll_window()`](../../backend_api_python/app/trade_discipline/manual.py) |
| 开仓、数量或归属证据不足 | `needs_review` | [`_observe_position()`](../../backend_api_python/app/trade_discipline/observation.py) |
| 无匹配的有效计划 | `proposed_exit / no_plan`，本轮跳过 EMA25 | [`check_plans()`](../../backend_api_python/app/trade_discipline/observation.py) |
| 缺下单时间或计划查询失败 | `needs_review / plan_evidence_unavailable` | [`PlanService.match_at_order_time()`](../../backend_api_python/app/trade_plans/service.py) |
| 有计划，EMA25 方向不符或收盘价等于 EMA25 | `proposed_exit / ema25_direction_blocked` | [`check_ema25_at_order_time()`](../../backend_api_python/app/trade_discipline/ema.py) |
| 有计划，行情缺失或无法验证 | `needs_review / ema_evidence_unavailable` | [`check_ema25_at_order_time()`](../../backend_api_python/app/trade_discipline/ema.py) |
| 计划和 EMA25 都通过 | 首轮 `waiting_for_next_poll`，后续符合条件时 `proposed_adoption` | [`apply_poll_window()`](../../backend_api_python/app/trade_discipline/manual.py) |

计划使用实际下单时已有的版本，按品种、交易所、产品、结算币和方向匹配。当前定时任务的计划匹配固定传 USDT。EMA25 使用下单前最后一根已收盘的 K 线，加密货币用 4 小时，股票规则在快捷开仓入口使用 1 小时。高于 EMA25 只允许做多，低于只允许做空。

## 拟退出与拟接管之后

- **退出**。开启自动退出后，Scheduler 用 [`queue_observed_exit()`](../../backend_api_python/app/trade_discipline/exit.py) 登记请求。Trading Worker 复核实时仓位、成交与归属，数量上限取本轮可确认值。发出请求前保存客户端订单号。超时或重启后，已提交记录按原订单号回查。
- **接管**。开启自动接管后，[`adopt_observed_position()`](../../backend_api_python/app/trade_discipline/adoption.py) 用原计划版本生成并校验参数，复核仓位、管理归属和未成交开仓单，再复用整仓接管流程。策略由原有策略命令启动，重复触发或异常恢复用接管键查找原实例。
- **查看一轮结果**。按 `round_started`、`snapshot_read`、`fill_replay`、`opening_origin`、`plan_check`、`ema25_check`、`position_decision`、`round_finished` 找终端日志。走了提前返回分支时，后面的判定日志会缺席。
