# 计划：技术与数据说明

更新日期：2026-10-25。描述已发布 v1 的实际结构；[模块入口](README.md)维护功能范围，[MCP 接入](MCP接入.md)维护工具和权限用法。此处不保留未实施的阶段方案。

## 模块边界和复用

- 后端集中在 `backend_api_python/app/trade_plans/`：领域服务、PostgreSQL 仓储、校验、Human/Agent 适配、交易事实读取与复盘摘要。
- 前端源位于独立 `QuantDinger-Vue` 仓库的 `src/views/trade-plans/`，复用现有请求、Ant 表单、品种搜索、市场身份、时区及本地化组件。
- MCP 适配为 `mcp_server/src/quantdinger_mcp/trade_plans.py` 和 `trade_plan_contract.py`，复用既有鉴权和传输。
- Human 路由 `/api/trade-plans`，Agent 路由 `/api/agent/v1/trade-plans`，两者调用同一服务。价格、数量和金额使用经校验的十进制字符串。
- 不新增长期任务、缓存、队列或通知。到期按读写时服务器时间判断；`TRADE_PLAN_MANAGEMENT_ENABLED=false` 可关闭计划 API，不停止交易。
- 快捷开仓原因继续使用 `app/services/quick_trade/history.py` 和 `qd_quick_trades.raw_result` 的 `_quick_trade.entry_reason`；不强制先建计划，不能把持仓接管理由写成开仓原因。

## 已实现规则

草稿只要求标题。进入观察要求市场、品种、方向、主策略、行情假设、入场/失效/退出/等待条件、支持依据及分析/决策周期完整。参考风险选填。

生命周期存储枚举：`draft / observing / cancelled / expired / completed`；到期还通过 `effective_lifecycle` 即时计算，不能只查 lifecycle 就断言计划仍有效。草稿和观察中可修订；观察中的新版本仍须文字完整。信号绑定内容版本，新版信号恢复未评估。取消、到期、结束后内容不可修订，可复制为新草稿；交易事实和复盘仍可追加。结束研究检查未闭合或归属未知的交易，取消不改变实际仓位。

首次保存具体品种后，六项标的身份不可更换或清空；仅标题草稿可首次补齐。分析引用的已知身份必须匹配；服务器读取本用户真实分析并冻结证据，调用方不能伪造系统摘要。

参考 1R = |参考入场价 − 初始止损价| × 基础资产数量；数量和风险预算二选一。仅观察为不适用，缺资料、方向/币种错误或不支持模型分别显示状态，不默算。1R 不含费用、点差和滑点，不将杠杆乘入价格风险。

交易登记固定采用版本和风险检查，后续修订不改分母；需结合真实入场时间核验事前性。单一成交、归档、执行事件和交易所成交身份不得重复归属；订单/策略引用不自动代表成交。来源缺失保留已采集快照，撤销或刷新不覆盖旧证据。 持仓管理策略来源兼容 exchange_config 内 credential_id 与旧 credentialId；账户信息按同用户读取，原生合约标识只取同策略、用户、账户、品种、产品和方向的真实持仓记录。匹配标识不唯一或缺失时保持不可确认，不从模板品种猜测。

只有闭合、归属清楚、成本与币种完整、事前风险可核验时才输出可信净收益/净 R。逐笔现货按买卖金额及核验费用计算；合约单位、资金费等不能完整核验时显示不可评估。文字复盘仍可保存。

## 七张表的完整字段

结构依据：`backend_api_python/migrations/20261023_trade_plan_management.sql`、`20261024_trade_plan_records.sql`；初始化结构同步在 `init.sql`。时间列为带时区时间，接口通常用 UTC，展示按用户时区。

关系：计划 → 多个版本/日志；计划 → 多次交易登记 → 多条关联/复盘。所有内部关系同时约束用户和计划归属。

### `qd_trade_plans`：计划主表

| 字段 | 类型 | 内容 |
| --- | --- | --- |
| `id` | `UUID` | 计划 UUID |

| `current_version_id` | `UUID` | 当前内容版本 |

## snapshot 内的业务字段

这些是 `qd_trade_plan_versions.snapshot` 的 JSON 键，不是额外的数据库列。

| 字段 | 内容 |
| --- | --- |
| title / primary_strategy | 标题 / 主要交易思路，分别最多 120 字 |
| hypothesis | 行情假设与自己的想法，最多 2000 字 |
| entry_trigger / invalidation / exit_rules / wait_conditions | 入场、失效、退出、等待条件，各最多 2000 字 |
| evidence / counter_evidence | 支持与反向证据，各最多 4000 字 |
| instrument | market、symbol、exchange_id、market_type、instrument_id、settlement_ccy 六项身份 |
| direction | long / short / watch；草稿可空 |
| analysis_timeframe / decision_timeframe | 分析与决策周期，沿用支持的周期枚举 |
| expires_at / retrospective / schema_version | 有效期、历史补录声明、结构版本 |
| research_refs | 最多 20 项；type 为 note / url / market_state_result；按类型保存 id、url、summary、data_as_of。市场分析另由服务器写入 evidence_snapshot、recorded_at |
| risk_inputs | model、entry_price、stop_price、target_price、quantity 或 risk_budget、currency、equity、equity_currency、equity_at；均可按需缺省 |

分析证据快照保存 id、market、symbol、exchange_id、market_type、instrument_id、timeframe、bar_close_at、trend、structure、summary。不是完整行情数据库的复制。

信号事件 payload 保存 status（unconfirmed / confirmed / withdrawn）、reason、assessment_author（human / ai_suggestion）。AI 建议不能冒充人工确认。复盘 assessment 保存 market_judgment、strategy_rules、execution，各有 value/reason，另有 improvement。

## 数据保护与请求恢复

版本、事件、交易登记、复盘在普通业务中只追加；关联只允许撤销标记变化，刷新通过撤旧加新完成。原管理员删除整个用户的既有语义仍可级联清理该用户数据，不扩大删除权限。策略或账户删除不级联抹除已保存的计划证据。

内容版本号 version_no 与并发号 row_revision 分开：内容修订增加版本号；状态、信号、关联等业务变更也增加并发号。修改带 expected_revision；旧基准和同键异参返回 409。身份变更与分析不匹配返回 422。

业务写入、日志、头部修订号与最小响应在同一个 PostgreSQL 事务中提交。用户级 request_id 保证重试回放；超时先查询原请求，不能直接换键重复创建。历史、引用、请求回放都重新检查当前用户及允许标的权限。
